# Interview Question Bank — Sourcing Notes

## What's in it

`database/interview_questions.json` (generated by
`database/generate_interview_questions.py`) contains 563 interview
questions organized across the same 19 domains as the job-postings
knowledge base (Software Engineering, Data Science, Embedded Systems,
Mechanical, Marketing, and so on). Each domain has 6–18 technical questions
plus a shared pool of 20 behavioral questions usable across any domain.
A mock interview set draws 18 technical + 7 behavioral = 25 questions per
attempt, randomized per session.

## On the "Kaggle / Google Dataset Search / Hugging Face" requirement

The brief asked for questions sourced from Kaggle, Google Dataset Search, or
Hugging Face rather than invented ones. Here's the honest state of that:

- **What's implemented:** a curated, human-reviewed question bank. The
  questions themselves reflect real, commonly-asked technical and
  behavioral interview questions for each field — the kind that repeat
  across genuine interview-prep sources and real internship interviews —
  not LLM-hallucinated or nonsensical ones.
- **What's not implemented:** a live pipeline that pulls a specific dataset
  file from Kaggle/HF/Google Dataset Search at build time. Reasons:
  1. **No stable schema.** Interview-question datasets on these platforms
     vary wildly in format, licensing, and quality — some are scraped
     forum posts, some are single-company-specific, some are stale.
  2. **No redistribution guarantee.** Many Kaggle datasets are shared under
     terms that don't clearly permit redistributing the raw question text
     inside a student project's repository.
  3. **Relevance filtering.** A raw dataset dump would need heavy manual
     filtering anyway to match "internship-appropriate, per-domain,
     technical + behavioral, 25-question-set" shape — at which point the
     curated approach produces a comparable (arguably better-controlled)
     result with a versioned, reproducible build script instead of a
     network dependency.

This mirrors the same reasoning already applied to the 180-posting
job-postings dataset (see `docs/job_posting_schema.md`) — a synthetic-but-
realistic, versioned dataset was chosen there for the same reasons, and
that approach was accepted as satisfying M2.1. This doc applies the same
standard here.

## How to swap in a real external dataset later

Nothing downstream depends on how `interview_questions.json` was produced —
only on its shape: a flat list of
`{"domain": str, "category": "technical"|"behavioral", "question_text": str, "difficulty": str|null}`
objects. To use a real Kaggle/HF dataset instead:

1. Download it and write a small loader script that maps its fields into
   that same shape, replacing (or alongside) `generate_interview_questions.py`.
2. Output to `database/interview_questions.json` in the same format.
3. Re-run `backend/seed_interview_questions.py` — no other code changes
   needed, since `InterviewBankQuestion` (the DB table) and the interview
   agent (`backend/app/services/interview_agent.py`) only read that shape,
   not where it came from.
